Contract hiện có (thứ cần bảo vệ):
- Envelope chuẩn `ApiResponse<T>` = `{ success, data, message, errors?, meta? }`, với `meta = { page, pageSize, total }` — `back-end/src/common/dto/api-response.ts`, tài liệu `docs/architecture/06-api-contract.md`.
- `PaginationQueryDto` đã có `page` (≥1, mặc định 1), `pageSize` (1–100, mặc định 20), `sort` (vd `createdAt:desc`), `q` — `back-end/src/common/dto/pagination-query.dto.ts`.

Khoảng trống thực tế (là lý do tồn tại của change request):
- **Public API chưa có tìm kiếm/lọc/phân trang.** `ExhibitsController` chỉ có `GET /rooms`, `GET /rooms/:slug`, `GET /rooms/:slug/exhibits/:exhibitId/model` — `back-end/src/modules/exhibits/controllers/exhibits.controller.ts`.
- **Thứ tự chưa chắc chắn ổn định ở nhánh search.** `searchAdminExhibits` sắp xếp `displayOrder ASC, createdAt DESC` (`exhibits.repository.ts:256`) — **thiếu tiebreaker duy nhất (`id`)** → cùng `displayOrder`/`createdAt` thì thứ tự không xác định, **phân trang có thể trùng/sót dòng**. (So sánh: `findList` ở `:85` dùng `displayOrder ASC, id ASC` — ổn định.)

→ **Vertical slice chọn làm:** thêm **endpoint public tìm kiếm hiện vật có lọc + phân trang + thứ tự ổn định**, tái dùng `PaginationQueryDto` + envelope `ApiResponse`/`ok(data, meta)`. Đây là slice nhỏ, chạy được, chạm đúng risk “đổi schema/API phá client cũ”.

## §A. Specification (phần 1 — 15đ)

**Problem statement (1 câu):**
> Khách tham quan và client 2D-fallback cần tìm hiện vật theo từ khóa, lọc theo phòng/trạng thái và duyệt kết quả theo trang với thứ tự ổn định; hiện Public API chưa hỗ trợ, buộc client tải toàn bộ rồi tự lọc — không mở rộng được và dễ vỡ khi dữ liệu tăng.

**Acceptance criteria (viết dạng kiểm thử được — 5 cái):**
- **AC-1 (search):** `GET /rooms/search?q=<kw>` trả về chỉ hiện vật **đã publish + visible** có nội dung khớp `q` (không phân biệt hoa/thường), trong envelope `ApiResponse` với `meta.total` đúng.
- **AC-2 (filter):** Lọc được theo `roomId` (UUID) và/hoặc `status`; input sai định dạng → **HTTP 400** + envelope `success:false` (không 500).
- **AC-3 (pagination):** `page`/`pageSize` hoạt động; `pageSize` > 100 hoặc < 1, `page` < 1 → 400; `meta` phản ánh đúng `page/pageSize/total`.
- **AC-4 (stable ordering):** Với dữ liệu có `displayOrder` trùng nhau, ghép các trang (page 1..n) **không trùng, không sót** một hiện vật nào (sắp xếp có tiebreaker `id`).
- **AC-5 (backward-compatible contract):** Response **giữ nguyên hình dạng envelope cũ**; không field bắt buộc nào bị xóa/đổi kiểu; endpoint cũ `/rooms/:slug` không đổi hành vi.

**Non-functional constraints (≥2):**
- **NFR-1 (Performance):** ở 150 tác vụ tìm kiếm đồng thời, **p95 ≤ 4.0 s**.
- **NFR-2 (Compatibility/Contract):** không breaking change với client cũ (envelope + field cũ giữ nguyên; field mới chỉ optional/additive).
- *(tuỳ chọn NFR-3 Security):* chỉ lộ dữ liệu published/visible; `q` được tham số hóa, không SQL injection.

**Invariant/contract quan trọng nhất cần bảo vệ (nêu rõ 1 cái):**
> **Thứ tự kết quả là một total order xác định (deterministic) với khóa phụ duy nhất `id`**, nên “union các trang = tập kết quả đầy đủ, mỗi phần tử đúng một lần”. Đây là invariant nền cho phân trang đúng; đồng thời **envelope/contract giữ backward-compatible** (risk trọng tâm). Contract testing sẽ chốt cả hai.

## §C. Risk-based Test Strategy + bảng test cases (phần 2 — 20đ)

**Phân bổ theo risk (nêu rõ cả test KHÔNG cần):**
- **Unit** (nhiều, nhanh): logic build query/sort parsing, map sort string → order, phân trang (skip/take), lọc published/visible. Mock repository.
- **Integration/API** (vừa — trọng tâm): endpoint thật + DB test (hoặc repository thật) để **bắt lỗi mà mock che giấu** (ordering, ILIKE, 400 vs 500).
- **Contract test** (bắt buộc): khẳng định **response khớp schema envelope** đã công bố; so field cũ còn nguyên (backward-compat). *Kỹ thuật test bắt buộc của VT-077.*
- **E2E**: 1 luồng “mở museum → search → sang trang 2” (nếu FE sẵn sàng). **Không cần** E2E cho mọi tổ hợp filter — đã phủ ở API/unit (ghi rõ lý do để lấy điểm “nêu test không cần thiết”).

**Cách chọn test data:** equivalence partitioning + boundary (theo Lecture 07):
- `q`: rỗng / khớp / không khớp / chữ hoa-thường / ký tự đặc biệt (`%`, `_` escape).
- `page/pageSize`: biên 0,1,2,20,100,101 (invalid <1, >100).
- `roomId`: UUID hợp lệ / sai định dạng / không tồn tại.
- Dữ liệu seed cố ý có **nhiều hiện vật cùng `displayOrder`** để test AC-4 (stable ordering).

## §E. Who tests the tests? — Mutation + Coverage + Flaky (phần 4 — 20đ)

**Mutation bắt buộc của VT-077 = “nuốt exception và trả dữ liệu mặc định”.** Làm ở **commit/nhánh tạm**, KHÔNG để lại trong nhánh nộp.

Mutation cụ thể: bọc thân `publicSearch` bằng `try { ... } catch { return ok([], {page,pageSize,total:0}); }` (nuốt lỗi, trả rỗng mặc định).
- **TC-12** (failure-path: repo ném lỗi) **phải FAIL** khi có mutation → chứng minh test bắt được. Lưu log.
- Nếu mutation **sống sót** (mọi test vẫn pass) → bổ sung/sửa test (assert phải **propagate lỗi**, không nhận `data:[]`), chạy lại, lưu log.
- Xoá nhánh mutation khỏi bài nộp; chỉ giữ evidence (log + diff dán trong phụ lục).

**Coverage (đặt trong context, không dùng tỉ lệ đơn độc):**
- Chạy `node --test --experimental-test-coverage` giới hạn `src/modules/exhibits/**` (mô phỏng theo script `test:coverage`). Báo line/branch coverage của file search.

**Flaky-test review (≥2 nguy cơ, gắn risk thật):**
- **Order/shared state:** test dùng chung DB/seed → chạy lại với thứ tự đảo (hoặc isolate transaction) để chứng minh không phụ thuộc thứ tự. (Liên quan trực tiếp invariant ordering.)
